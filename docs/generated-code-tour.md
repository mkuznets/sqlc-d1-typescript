# Generated-code tour

This tour uses the public API generated by the [canonical `users` Worker](../examples/d1-worker/). Generated files contain implementation details, but consumer code should depend only on exported argument/row types, query factories, query descriptors, query executors, sessions, and public errors.

## 1. Generated argument and row types

A query's named or positional parameters become a required object when arguments exist. Projected columns become a row interface.

<!-- compile: tour-get-user-types -->
```ts
export interface GetUserArgs {
  id: number;
}

export interface GetUserRow {
  id: number;
  name: string;
  nickname: string | null;
}
```

These declarations are generated from `GetUser`. Nullable properties are still required when used as arguments; SQL `NULL` is `null`, not omission or `undefined`.

## 2. A factory constructs a query descriptor

<!-- compile: tour-construct -->
```ts
import { getUser } from "./queries_sql";

const query = getUser({ id: 1 });
```

`getUser` validates its bind values synchronously and snapshots mutable values. It does **not** contact D1. The returned query descriptor is opaque: pass it to a query executor rather than inspecting or constructing its representation.

A validated descriptor can be reused. Its snapshotted arguments do not change if caller-owned input is later mutated.

## 3. A query executor calls D1

<!-- compile: tour-execute -->
```ts
import { DB } from "./runtime";
import { getUser, type GetUserRow } from "./queries_sql";

declare const binding: D1Database;
const db = new DB(binding);
const user: GetUserRow | null = await db.execute(getUser({ id: 1 }));
```

`DB` wraps a Workers `D1Database` binding. `execute` prepares, binds, and runs the descriptor, then checks and maps the returned data into a fresh public row object.

## 4. Command results are visible in descriptor types

| sqlc command | Result from the query executor |
|---|---|
| `:one` | `Row \| null` |
| `:many` | `Row[]` |
| `:exec` | `void` |
| `:execrows` | safe-integer `number` from `meta.changes` |
| `:execlastid` | safe-integer `number` from `meta.last_row_id` |
| `:execresult` | native `D1Result<Record<string, unknown>>` |

For the canonical queries:

<!-- compile: tour-command-results -->
```ts
import { DB } from "./runtime";
import {
  getUser,
  listUsers,
  renameUser,
  type GetUserRow,
  type ListUsersRow,
  type RenameUserRow,
} from "./queries_sql";

declare const binding: D1Database;
const db = new DB(binding);

const one: GetUserRow | null = await db.execute(getUser({ id: 1 }));
const many: ListUsersRow[] = await db.execute(listUsers());
const renamed: RenameUserRow | null = await db.execute(
  renameUser({ name: "Ada", id: 1 }),
);
```

## 5. Row mapping is checked

The generated mapper requires every projected field and validates its physical representation. Contradictory or missing result data throws `QueryResultError`; it is not silently cast into the row interface. BLOB outputs and mapped row objects are fresh copies.

A native D1 rejection passes through unchanged. See [runtime and errors](runtime-and-errors.md) before adding retry behavior, especially for writes.

## 6. A static batch preserves positions

<!-- compile: tour-static-batch -->
```ts
import { DB } from "./runtime";
import {
  getUser,
  listUsers,
  renameUser,
  type GetUserRow,
  type ListUsersRow,
  type RenameUserRow,
} from "./queries_sql";

declare const binding: D1Database;
const db = new DB(binding);

const results: [GetUserRow | null, ListUsersRow[], RenameUserRow | null] =
  await db.batch(
    getUser({ id: 1 }),
    listUsers(),
    renameUser({ name: "Ada", id: 1 }),
  );
```

One native atomic D1 batch call executes the non-empty tuple. Each output position retains the corresponding descriptor's result type. The [runtime guide](runtime-and-errors.md#batch-shapes) also covers a stable meaningful head with a dynamic homogeneous side-effect tail.

## 7. A request-flow-local session exposes a bookmark

<!-- compile: tour-session -->
```ts
import { DB } from "./runtime";
import { getUser } from "./queries_sql";

declare const binding: D1Database;
declare const incomingBookmark: string | undefined;

const session = new DB(binding).withSession(incomingBookmark);
const user = await session.execute(getUser({ id: 1 }));
const outgoingBookmark: string | null = session.getBookmark();
void [user, outgoingBookmark];
```

Start with no argument, `"first-primary"`, `"first-unconstrained"`, or an opaque bookmark string. Keep the session executor inside one request flow, await operations in required order, and transfer only the bookmark string between requests. A session is not a transaction.

## 8. Failures identify the phase

```text
factory(args)
  └─ QueryArgumentError (synchronous; D1 not called)
executor.execute(descriptor) / executor.batch(...descriptors)
  ├─ QueryUsageError (invalid use)
  ├─ native D1 rejection (same error object)
  └─ checked mapping
       └─ QueryResultError (D1 already returned successfully)
```

A `QueryResultError` after a write is not rollback evidence and does not make an automatic retry safe.

## Mental model

1. sqlc analyzes schema and SQL.
2. The Plugin translates supported metadata into TypeScript.
3. A generated factory validates arguments and returns an opaque query descriptor.
4. `DB` or a session executor executes it through a Workers binding.
5. Generated mapping checks native results and returns the public type.
